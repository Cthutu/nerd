# M3: concurrent LLVM rendering and semantic snapshot fixes

2026-09-20, Linux x86-64, Ryzen 9 7950X, LLVM 22.1.8. Baseline `06a989e3`
compared with that commit plus this render-ownership slice. Both benchmark
compilers are release builds. [Raw comparison](compiler-m3-render/comparison.json.gz)
retains compiler hashes, commands, samples, phase records and output hashes.

## Audit findings and fixes

`sema_materialise_type` accepts a const Sema pointer but casts away const and
can append type data. The LLVM snapshot previously copied types, parameter
types, symbols and values, leaving six mutable arrays borrowed. The snapshot
now also copies braced-payload flags, four bitfield metadata arrays and plex
uses. Cleanup frees every owned array. The regression constructs abstract record
and enum types and materializes them in a private copy, checking independent
storage, appended metadata and unchanged original counts/values.

Imported constant expressions and imported default-argument expressions can
enter the same materialization helpers. They now use scoped semantic copies;
default copies are created only when a default expression is actually emitted.
Their surrounding HIR, lexer and non-type semantic tables remain borrowed.
Imported symbol lookup, display-trait identification and generic signatures use
read-only source-table operations. The generic signature path renders types and
layout; it does not invoke the materialization paths used by expressions.

AddressSanitizer also exposed a pre-existing serial front-end use-after-free in
Quill: inference of a record field can append to/reallocate the semantic type
array while the enclosing record literal retains a pointer into it. That path
now keeps a value copy of the record layout across recursive field inference.
The sanitizer suite includes Quill so this failure stays covered.

The review followed the renderer's external semantic and lexer calls:
materialization is the mutating semantic entry point; classifiers, type names,
symbol lookup and indexed line lookup are read-only on borrowed inputs. Type
names allocate in the supplied or nested local arena. Renderer file-static data
is constant. Builders, debug metadata and function state belong to a render;
shared allocation bookkeeping is synchronized. No global temporary-arena use
was found on the nonfatal render path. Diagnostics remain task-owned captures;
rendering them and emitting profiling records remain coordinator operations.
Fatal internal errors still terminate the process.

Input registry, HIR, lexers, source indexes and non-type semantic tables must be
frozen during dispatch. The emission-scoped function-name map is built before
workers start and remains alive until all joins complete. Its map lookup does
not mutate entries. These invariants must also hold on scheduler failure paths.

## Concurrent harness

`build/test_render_threads.py` invokes an internal compiler test; ordinary build
commands still render serially. The harness loads/checks/lowers sources once,
constructs the name index, and renders serial references. It releases waves of
up to four native workers through a condition-variable gate, with two jobs
sharing each module's input. This tests both cross-module access and simultaneous
reads of one module. Each task owns its arena, diagnostic context and finished
metrics. Every wave joins before coordinator comparison/cleanup.

All four debug/export flag combinations are checked, with reversed module order
on alternate variants. Worker output must match the serial reference byte for
byte. A fresh serial render after worker cleanup must also match. Fingerprints
of all ten original semantic type arrays are checked after every variant.
Unexpected diagnostics fail the test. Cleanup joins before freeing task storage,
name indexes or the loaded program. The harness has no detached threads or
external LLVM-tool execution; it tests source-to-IR ownership directly.

Inputs include tiny, wide, deep and large synthetic programs; Dungeon, Pixels
and Quill; embedded/generic plex fields, generic functions and enum discriminants;
and a generated imported-constant/default-argument program. The ordinary harness
runs in `just test`. `--sanitize thread` and `--sanitize address` build isolated
instrumented copies of the actual compiler with project source/define discovery,
then run the same matrix. Embedded runtime objects must first be generated by a
normal compiler build. These sanitizer builds do not replace installed binaries.

This is evidence for the exercised inputs, not a universal race-freedom proof.
Native Windows/macOS validation and scheduler queue/cancellation/worker-count
stress remain pending. No scheduler or `--jobs` option is enabled in this slice.

## Serial overhead

```sh
cp _bin/nerd /tmp/nerd-m3-render-before
just build-release nerd --skip-mod-sync
python3 build/benchmark_compare.py --before /tmp/nerd-m3-render-before --cpu 2 \
  --output /tmp/nerd-m3-render.json
```

One warm-up, five alternating unprofiled samples and one separate profile per
compiler for each of 14 workload/target cells. Warm CPU-2 runs with no competing
tests/builds; frequency and SMT activity were not fixed. Both compilers use the
same sources, paths, checkout modules and direct LLVM tools. Target settings are
independent of compiler build settings. Generated programs are not executed by
the benchmark; the full suite checks correctness separately.

Times include IR writing, object generation and linking. Positive change means
slower. RSS is the median maximum per-process high-water mark for the compiler
and waited-for children, not their simultaneous sum or isolated snapshot storage.
No multicore scaling or compilation speedup is claimed by the stress harness.

All 196 benchmark invocations produced byte-identical combined LLVM within their
cell. The additional copying has a modest observed cost on some inputs: Pixels'
debug target is about 2% slower here (4.56 ms). Other changes are small and mixed;
no speedup is claimed. Peak-process RSS is essentially unchanged at this
measurement resolution.

Linux validation: `just test` passed with 1,120 compiler tests and nine skips,
core concurrency tests, the new render harness, profiling/output parity,
direct LLVM/no-Clang and doctor checks, installation smoke tests and 279 C
compatibility fixtures at both optimization levels. CodeLLDB stepping passed.
Full-compiler ThreadSanitizer and AddressSanitizer render matrices passed after
the ownership and serial inference fixes. This completes the Linux M3 gate;
M4 is next. Native Windows/macOS validation remains pending.
The uninstrumented concurrent-render matrix also passed with the release compiler.
